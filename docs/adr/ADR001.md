# ADR001: Sans-IO core, hand-written async, one crate

**Status:** Accepted

## Context

mettle is a resilience toolkit, and retry is the first tool in it. Before writing much, we had
to settle how the retry engine would be built: easy to test, not married to one async runtime,
and with room for more tools (including a sync version) without tearing things up later.

## Decisions

**1. Keep the decision logic pure; inject time through a `Clock` trait.**
The backoff math and the "should we retry?" logic touch no I/O. They don't sleep and they
don't read the clock. Time comes in through a `Clock` trait with `now()` and `sleep()`, and
only the driver calls it.

The reason is testing. Retries are all about waiting, and if the tests wait on the real clock
they're slow and flaky. With a mock clock a test jumps "now" forward and finishes sleeps
instantly, so it can check the exact sequence of delays without ever waiting. Anyone on a
non-Tokio runtime just writes their own `Clock`.

**2. Write the `Future` by hand instead of boxing an `async fn`.**
The async driver, `RetryFuture`, is a hand-written `poll` state machine over an enum of phases
(`Idle`, `Attempting`, `Sleeping`), pin-projected with `pin-project-lite`.

The easy version would be an `async fn` boxed as `Pin<Box<dyn Future>>`. We didn't do that,
because it allocates, dispatches through a vtable, and forces `Send + 'static` onto the
caller's operation. Writing the future ourselves lets the operation borrow local state and
skip `Send`; the whole future is `Send` or `'static` only when its pieces are. It costs us
more code, the `pin-project-lite` dependency, and a nameable `Clock::Sleep` type (a
hand-written future needs concrete field types, so the sleep future has to have a name).

**3. Async and blocking run on the same decision core.**
The blocking driver calls the same pure `should_retry_after` and emits the same per-retry
`tracing` event as the async one. All that differs is how they wait: the async side polls, the
blocking side calls `thread::sleep`.

Since the decision logic is already I/O-free, a second driver was cheap to add, and sharing it
means the two can't quietly grow apart. It's also why blocking ships in 0.1 instead of waiting
for its own release. On its own it's too small to version separately.

**4. One crate, flat modules.**
Everything lives in a single crate with flat modules: `backoff`, `clock`, `retry`, `blocking`.
No workspace, no hexagonal folder tree. The design is still hexagonal in spirit, since `Clock`
and `Backoff` are the ports, just without the scaffolding. We'll split out a sub-crate when
something genuinely needs to be separate, not before.

## Consequences

The core tests fast and runs on any runtime, the async path allocates nothing and can borrow,
and the blocking driver reuses the decision logic rather than copying it, so the two stay in
sync. What we pay for that is a hand-written state machine to keep working and the
`pin-project-lite` dependency.
