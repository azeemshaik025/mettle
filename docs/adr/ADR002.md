# ADR002: Public API, open traits, one validated `Backoff`

**Status:** Accepted

## Context

The public API is what users touch, and once 0.1 is out we're stuck with it. It should make
the easy case easy and stay open for people who need more, without handing anyone a footgun.

## Decisions

**1. `retry(op).await`, via `IntoFuture`.**
`retry(op)` hands back a builder with sane defaults. Adjust it with `.backoff()`, `.clock()`,
`.when()`, and `.max_elapsed()`, then just `.await` it, since the builder implements
`IntoFuture`. The blocking version ends in `.call()` because there's nothing to await. The
point is that the smallest useful call is `retry(op).await`, with no policy object to set up
first, and every override is a builder method you find by autocomplete.

**2. Traits stay open, not sealed.**
`Backoff` and `Clock` are unsealed. They're meant to be extended: a custom strategy, a mock
clock, a clock driven by a simulation. This door only opens one way. Going sealed to open later
wouldn't break anyone, but open to sealed would, so leaving them open is a real commitment.
We're fine with that, because being extensible is half the point of the crate.

**3. One `Backoff` trait, taken by value.**
There's a single `Backoff` trait and a single `ExponentialBackoff` type that holds both the
validated config and the running state. An earlier design had two traits: `Backoff` plus a
`BackoffBuilder` whose `build()` produced a fresh sequence per run. That was three types just
for exponential backoff (config, builder, running sequence) and made every custom strategy
implement two traits. Collapsing it dropped a trait, a type, and a `B::Backoff` associated type
from every signature, so a custom strategy is now one impl. Since `retry` owns `self`, it takes
the backoff by value and drives that instance, which means no clone and no `Clone` bound. Want
to reuse a policy across calls? Pass a fresh one, or clone it yourself.

**4. Validate the backoff config when it's built.**
`ExponentialBackoff::new()` checks the config and returns `Result<_, BackoffConfigError>`, and
`factor` is a `NonZeroU32` so a zero can't even be written down. A zero `base` or `factor`
would make every delay zero, turning the retry loop into a busy-loop that hammers the
dependency as fast as the CPU can go. That's a denial of service you point at yourself, and
nothing downstream would notice. Catching it at construction means any `ExponentialBackoff`
you're holding is already valid. The delay math also saturates instead of panicking if it
overflows.

## Consequences

The happy path is one line, the extension points are open, and the whole backoff story is one
trait and two types. You can't build a config that busy-loops. The two things we can't walk
back after 0.1 are the open traits and the by-value signature.
