# ADR003: Dependencies and Cargo features

**Status:** Accepted

## Context

What mettle depends on is also what it forces on everyone who uses it, so dependencies are
part of the API too. Two questions here: how do retries show up for logging and metrics, and
who has to pay for the async runtime?

## Decisions

**1. Observability through `tracing` events.**
Every retry emits one event: a `warn!` on the target `mettle::retry`, carrying the attempt
number, the delay, and the error. `tracing` is a required dependency, but only its `std`
feature, so no proc-macro comes along. There's no span owned by mettle. With this, any
subscriber sees retries, you can filter them with `RUST_LOG=mettle::retry=warn`, and it costs
almost nothing when nobody's listening. An event rather than a span means it picks up the
caller's span context for free, and we can still add a span later if we want one. The only cost
is an `E: Debug` bound on the terminal calls, which everyone has anyway.

**2. `async` and `blocking` are features, and `tokio` lives behind `async`.**
Both features are on by default. `async` brings in `tokio` (and `pin-project-lite`); `blocking`
brings in nothing extra. A `compile_error!` fires if you turn both off. This wasn't the
original plan. `TokioClock` needs Tokio's timer, so back when mettle was async-only, Tokio was
just a hard dependency and that was fine. Then the blocking API landed, which needs no runtime
at all, and suddenly sync-only users were dragging in Tokio for nothing. So it moved behind the
feature. A sync-only build is now `default-features = false, features = ["blocking"]`, with no
Tokio and no runtime, and people on defaults don't notice any change.

## Consequences

Retries are visible out of the box for the price of one small dependency with no proc-macro.
Default users get everything; sync-only users can drop the runtime. The feature names `async`
and `blocking`, and the `mettle::retry` tracing target, are things people build against now, so
we're on the hook to keep them stable.
